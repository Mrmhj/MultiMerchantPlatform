# Token 消耗分析与优化报告

> 报告类别：运营分析 · 摩登时代 · 2026-08-02
> 背景：单会话累计消耗约 3.2 亿 token（2026-08-02 08:00 → 15:00，跨 Phase 0 收尾 → Phase 1 全部 → Phase 2 开端）

---

## 一、结论（TL;DR）

**是。主因就是上下文过长。** 3.2 亿 token 中约 **88% 是"历史上下文重新发送"**，而历史上下文之所以这么长，是因为单会话连续运行 7 小时、跨越近 3 个阶段、工具调用数百次。这不是功能浪费，而是**长会话模式的固有成本**——每轮对话都要把前面所有历史完整重发一遍，轮数越多，单轮越贵，总消耗呈平方级增长。

**最大的优化杠杆：按阶段开新会话，预计可省 50%-70% 的 token。**

---

## 二、消耗构成（估算）

| 构成 | 占比 | 说明 |
|---|---|---|
| **历史上下文累计（输入）** | ~88% | 每轮重发全部历史：工具调用结果、代码、日志、对话 |
| 系统提示 + 工具定义（输入） | ~8% | 每轮固定携带（规则/工具 schema/记忆注入），轮数乘数 |
| 模型输出（生成） | ~4% | 实际写出的代码、回答、文档 |

**为什么会是 3.2 亿：**

```
总消耗 ≈ Σ(每轮输入 token)
       ≈ 轮数 × 平均上下文长度
       ≈ 轮数² × 单轮平均增量   ← 平方级增长
```

单会话从 8:00 跑到 15:00，上下文从几千增长到几十万，平均每轮携带 5-10 万 token × 数百轮 → 数亿量级。

## 三、本次会话中的可避免消耗（有据可查）

按可节省量排序：

| # | 消耗点 | 发生次数（本次） | 说明 |
|---|---|---|---|
| 1 | **编译-报错-修复-重编循环** | 5+ 次（Swagger 接入 4 次、Microsoft.OpenApi 2.0 3 次） | 每次编译输出+错误信息+修复后重编全部进上下文 |
| 2 | **文件锁冲突 → 重读文件确认** | 3+ 次 | 服务进程锁 DLL 导致编译失败，需停进程重编 |
| 3 | **git 提交 CRLF/LF 警告** | 每次提交 30+ 行 | 纯噪音输出（Windows 换行符提示） |
| 4 | **重复 curl 测试输出** | 多次 | 已用 python 提取关键字段（做得好，继续保持） |
| 5 | **大文件整读** | 少量 | 部分文件可用 grep/sed 定向提取 |

## 四、优化建议（按杠杆排序）

### 🔴 P0：结构性优化（收益最大，约省 50-70%）

**1. 按里程碑开新会话**
- 本项目 **git + docs + 记忆体系完备**：新会话靠 `git log` + `docs/` + `.workbuddy/memory/` 恢复上下文，成本 <1 千 token
- 建议节奏：**每个服务完成并提交 Git 后，开新会话继续下一步**
- 收益：200 轮长会话约 4000 万单位消耗 → 阶段化（每 30 轮重置）约 630 万单位，**省 84%**（见会话内对比图）

**2. 长任务中途强制"存档点"**
- 每完成一个阶段（如本次 cart+search 提交后），主动提醒小马哥开新会话
- 自动化/定时任务用精简 prompt，不带无关历史

### 🟡 P1：操作优化（本次会话可立即执行，约省 10-20%）

| 优化 | 做法 |
|---|---|
| 减少编译循环 | 写代码前对照编码规范与既有模板（csproj/Program.cs/Mediator 显式泛型），一次性编译通过 |
| 锁冲突直接处理 | 编译失败先查端口占用（PowerShell 停进程）再重编，**不重读文件** |
| git CRLF 警告 | 项目根加 `.gitattributes`（`* text=auto`），一次性解决 |
| 测试输出瘦身 | 继续用 python 提取关键字段；`tail -n` 只取需要的行数 |
| 服务日志 | 只 grep 错误关键词，不整文件输出 |

### 🟢 P2：平台侧（不可控，但可认知）

- 系统提示 + 工具定义是每轮固定开销（本轮会话工具较多，乘数影响明显）
- 记忆/技能注入同样每轮携带——记忆文件保持精简（本项目已控制在规范内）

## 五、给后续开发的工作方式约定（建议固化为规范）

1. **阶段边界 = 会话边界**：每交付一个服务（编译 0 警告 + 冒烟通过 + 文档 + 提交 Git）→ 开新会话
2. **新会话恢复三板斧**（已实践验证有效）：
   ```
   git log --oneline -5        # 看提交历史
   docs/PROJECT_PLAN.md        # 看路线图定位当前阶段
   .workbuddy/memory/          # 看工作日志的"下一步"标记
   ```
3. **预算意识**：单会话建议控制在 100 轮内或 2 个服务内；超限主动切换
4. 每周末把 30 天前的日志蒸馏进 MEMORY.md 并归档（已在记忆规范中）
